## Protocolo confirmado
Frontend mantém chave por usuário/plano/prazo/método/cupom em localStorage (billing.service.ts). Mesmo outra chave não contorna a compra: prepare_* resolve aliases e a tentativa pendente do usuário sob locks SQL, validando condições. Reserva, pagamento, preço e tentativa são transacionais. Snapshot fixa total em centavos, prazo, indicação ou afiliado e fundador. As configurações atuais não reprecificam a tentativa.
claim é CAS prepared -> submitted ANTES do POST. Somente true autoriza Pix /v1/payments ou cartão /checkout/preferences; chave mp-prepaid-{payment_id}, referência payment:{payment_id}:subscription:{subscription_id}. Outro chamador faz busca GET por referência e GET por ID, nunca POST. Busca vazia não libera a tentativa.
Após validar referência/moeda/total, Pix terminal passa pelo processApprovedPayment (que relê oficialmente o pagamento). complete_* grava URL/ID/resultado, preserva status que webhook já gravou e devolve status local. ready recupera resultado sem novo POST. Aprovação/benefícios permanecem nas funções e ledger existentes; nenhuma migration alterada.
Recuperar compra anterior busca a tentativa mais recente daquele usuário/plano e reaproveita método, prazo, chave e cupom persistidos. Não muda de Pix para cartão para escapar de pendência.

## Defeitos corrigidos
- Catch ocultava causa: agora conserva cause internamente e registra etapa, operação de busca ou detalhe, categoria segura, HTTP, trace permitido, duração total e correlation_id. Não registra mensagens brutas, referências, usuário, preço, corpo, QR, tokens ou dados pessoais. Exceções SQL transitórias deixaram de ser sempre BAD_REQUEST; código SQL permitido acompanha o diagnóstico.
- JSON inválido de HTTP de erro apagava o status original: agora mantém HTTP e x-request-id sanitizado. Busca e detalhe têm operações distintas. Múltiplos resultados/ID ausente/resposta inválida/referência divergente têm categorias próprias.
- Primeira preferência de cartão não validava itens/valor/moeda/referência; agora exige as mesmas condições da recuperação. Pix já validava; agora cada divergência é identificável. Claim malformado não pode autorizar POST. Resultado vazio da persistência não é sucesso.
- Interface de recuperação ignorava mudança de seleção/plano e permitia repetir indefinidamente: resultado só é aplicado à identidade e versão atuais, trava imediata impede cliques simultâneos e até três consultas manuais são permitidas por montagem da tela. Refresh pode reiniciar o contador visual, mas sempre recupera a mesma tentativa persistida; nenhuma mutação é reproduzida automaticamente.
- Mensagens distinguem indisponibilidade temporária, ausência de recurso confirmado e revisão pelo suporte. Rejeição HTTP mantém resultado local conservador: não concede acesso nem automaticamente libera nova compra. Mesmo falha comprovadamente anterior ao POST (configuração ausente) permanece para revisão; política de reenvio não foi ampliada.
